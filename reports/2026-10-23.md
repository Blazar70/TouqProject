## 3. Bugs (new)

**B6 — Medium — The default "Paid at" time is when the page was opened, not when the money was taken**
- `src/pages/PaymentsPage.tsx:92` sets `paidAt` once, when the page first appears. It is reset only after a successful save (`:329`). That value goes to `create_invoice(p_paid_at)` (`:296`), and the database stores it as the payment time (`0062_invoice_list_prices.sql:131`).
- Scenario: a receptionist opens Payments at 08:30 and takes the first payment at 11:15 without touching the field. The payment is stamped 08:30. If the tab was left open overnight on the front-desk tablet, the first payment of the morning lands in **yesterday's** cash-up.
- Fix: send no `p_paid_at` unless the user actually changed the field, so the database uses `now()`. Better still, see S7.

**B7 — Low — Two ways of paying record the time differently**
- `create_invoice` uses the time sent by the client. `add_invoice_payment` (0061, the later "Add payment" on an existing invoice) always uses `now()`. That half of S7 is fine, but staff will find it confusing that one path has a time field and the other does not.
- Fix: same as S7 (one rule for both).

Checked and fine:
- `create_invoice` now takes the list price from `services` (0062).
- The totals and the VAT spread add up. The rest left by rounding goes on the biggest line.
- Payments can't exceed the total.
- `add_invoice_payment` and `create_credit_note` lock the invoice row (`for update`), so two clerks can't overpay at the same time.
- The owner-balance ledger locks the owner row and can't go below 0 (checked both in the trigger and by a check constraint).
- `merge_owner_files` locks both rows in id order, so two merges can't deadlock.
- `owner_files.balance` can't be written by the app: the column grants allow only name, phone, email and notes.
- Report functions are `security invoker`, so RLS applies (the database's row-level security rules), and their day boundaries are computed in `clinics.timezone`.
- The ZATCA QR TLV uses the length in UTF-8 bytes.
- Print HTML escapes every user text.
- `purgeClinic` still works with the new tables: `invoice_payments` and `credit_notes` cascade from invoices, `owner_files` and `doctor_time_off` cascade from clinics, and `appointment_services` cascades from appointments.

## 4. Security (new)

**S6 — Medium — Credit notes have no role check and no limit, so the staff discount cap can be bypassed**
- `create_credit_note` (`0061_invoicing_core.sql:358-412`) checks only that the invoice belongs to the caller's clinic. The UI shows the credit-note action to every role (`src/components/InvoiceDetail.tsx:145`, with no `isManager` check).
- Meanwhile `create_invoice` limits non-managers' discounts to `clinics.max_staff_discount_percent` (10% by default). Top-ups are limited to receptionists and managers (`0064:122`).
- Scenario: a nurse bills 1,000 SAR (cash, paid). One minute later the nurse issues a credit note for 600 SAR with "refund: cash" and the reason "goodwill". That is a 60% discount, and 600 SAR leaves the drawer. With "refund: balance", the money moves into an owner's prepaid balance, which can then pay another pet's bill. It is logged in `admin_audit_log`, but nothing stops it.
- Fix: in `create_credit_note`, require `current_user_has_role(array['manager'])`, or apply the same `max_staff_discount_percent` test to `v_amount / amount_total` for non-managers. Hide the button the same way in `InvoiceDetail.tsx`.

**S7 — Medium — Any staff member can set any payment time, including in the past or future**
- `create_invoice(p_paid_at)` (`0062:15,131`) stores whatever time the client sends, with no range check. The cash-up report (`0065_reports.sql:43`) and the income report (`:178`) group by `paid_at`.
- Scenario: the day's cash-up was counted and signed off at 21:00. The next morning someone records a 300 SAR cash payment dated yesterday 20:00. Yesterday's report now shows 300 SAR more than the drawer had, and the "who and when" trail is just `received_by`, with the real entry time not stored.
- Fix: drop `p_paid_at` (always `now()`), or allow only managers to backdate, at most N days, and add `invoice_payments.created_at` (it exists already, so also show it on the invoice when it differs from `paid_at`).

**S5 (follow-up)** is still open; see section 5.

- `merge_owner_files` and credit notes are also open to every role. Phase 4 should cover them together with S6.

## 6. HCI / visual / usability ideas

**H6 — Accept Arabic digits in money and quantity fields** (S)
- Problem: the amount, price, quantity and discount inputs are `type="number"` (`PaymentsPage.tsx:375,502,513,599,694,698`). With an Arabic keyboard, iOS/Android type ٠١٢٣…, which a number field rejects or empties without saying anything. The code base already converts these digits for clinical fields (`src/lib/clinicalFields.ts:27`).
- Who: Arabic-speaking receptionists, the busiest users of Payments.
- Change: use `type="text" inputMode="decimal"` and run the existing digit conversion (move it to a small shared helper) before `parseFloat`.

**H7 — "Counted cash" box on the daily cash-up** (S–M)
- Problem: `ReportsPage.tsx` (cash-up) shows what the drawer *should* hold, but the receptionist must compare it with the real count by hand or on paper. Nothing records a shortage.
- Who: receptionists closing the day, managers reviewing.
- Change: one number input per branch for counted cash, with the difference shown in red or green. Saving it to a small `cash_counts` table (day, branch, counted, by) would make the close-of-day step real, and pairs well with S7.

**H8 — Make the "Paid at" field opt-in** (S)
- Problem: every new invoice shows a required date-time field (`PaymentsPage.tsx:627-628`) that 99% of the time should just be "now". It costs attention and causes B6.
- Who: receptionists.
- Change: show "Paid now · change" as a link. Only clicking it reveals the field, and only managers can do so (ties into S7).

**H9 — Show the owner's balance next to the "Balance" payment method, and offer "Use balance"** (S)
- Problem: the balance appears as a note under the pet picker (`PaymentsPage.tsx:451`). The user still has to type the amount in the payment row and check that it isn't too much (the error appears only on save, `:276`).
- Who: receptionists with prepaid owners.
- Change: when the method is "balance", pre-fill `min(balance, remaining)` and show "available: X SAR" in the row itself.

**H10 — Confirm before issuing a credit note, with a plain preview** (S)
- Problem: a credit note can't be undone (correctly). The dialog should say in one sentence what will happen: "Credit 600.00 SAR on INV-MAIN-000123; 600.00 SAR goes back in cash", before the final tap.
- Who: everyone billing, especially on tablets where mis-taps happen.
- Change: reuse `ConfirmContext` (`src/lib/ConfirmContext.tsx`) in `InvoiceDetail.tsx` before calling `create_credit_note`.

Notes:
- SAMA rules (seen in snippets) cap mada charges for acquirers at **0.8%, max SAR 40**. An acquirer is the bank-side company that processes card payments. Whether the cap applies to online gateways is unclear, so ask each vendor for a mada e-commerce quote.
- **Tap to Pay on iPhone** was announced by SAMA in September 2026 as "coming soon" in KSA, with no provider named. Today, a phone as a terminal means Android SoftPOS.
- Touq fit: all of them follow the same pattern.
  1. An edge function creates the payment or link server-side (the secret key never reaches the browser).
  2. The gateway calls a webhook edge function.
  3. That function **re-fetches the payment by id**, then calls `add_invoice_payment`.
  - Add `provider` and `provider_payment_id` to `invoice_payments` (a new migration) so a vendor switch is cheap, and so the same webhook can't be counted twice (make the id unique).
- Sources: https://moyasar.com/en · https://docs.moyasar.com/ · https://developers.tap.company/docs/webhook · https://sama.gov.sa/en-US/News/Pages/News-578.aspx · https://geidea.net/merchants/en/through-android-phone · https://geidea.net/ksa/en/solutions/payments/softpos · https://docs.geidea.net/ · https://hyperpay.docs.oppwa.com/tutorials/webhooks/decryption-example · https://www.qoyod.com/en/blog/online-stores/comparison-of-electronic-payment-gateways/ · https://sama.gov.sa/en-US/MediaCenter/News/Pages/news-1170.aspx

**Recommendation (C):**
- Nothing to build until a real clinic wants online deposits. Card payments at the desk keep using the terminal and the existing "card" method.
- When it is needed, ask **Moyasar and Tap** for written mada and card quotes, since both are the simplest to wire to a Deno function. Ask **Geidea** too if the clinic wants one provider for its terminal, SoftPOS and online payments.
- Build only the payment-link flow first (no card form inside Touq). That keeps Touq out of PCI card-data scope (PCI is the card industry's security standard).

### D) Error monitoring (Vite React PWA + Supabase edge functions)

Why it matters: today an error on a receptionist's tablet is invisible to you. Once Touq is hosted, you need to see crashes and failed RPCs with the screen and version they came from.

| Service | Price (seen 2026-10-23) | Data region | Effort | Lock-in / risks |
|---|---|---|---|---|
| **Sentry** | Free Developer plan: 1 user, 5k errors/month, 30-day history. Team $29/month (or $26 billed yearly): 50k errors, unlimited users (sentry.io/pricing, fetched) | US or **EU (Frankfurt)**, also on the free plan. No KSA region | **S**: `@sentry/react` + `@sentry/vite-plugin`; `npm:@sentry/deno` in edge functions | The Deno SDK can mix up concurrent requests; use `withScope` and turn off default integrations (Supabase guide, snippet) |
| PostHog error tracking | 100k exceptions/month free (pricing doc, snippet) | US/EU (unverified) | S–M | Worth it only if you also want product analytics |
| Better Stack | 100k exceptions included; paid from about $25–30/month (unverified) | unverified | S | Accepts the Sentry SDK, so you only change the DSN (the project address errors are sent to) |
| GlitchTip | Self-hosted free (open source); hosted from about $15/month (unverified) | **Anywhere, including a KSA server** | M (you run the server) | Fewer features; you maintain it |

Notes:
- **Source maps** (files that turn minified code back into readable lines): set `build.sourcemap: 'hidden'` and put `sentryVitePlugin` last in `vite.config.ts`. Use `filesToDeleteAfterUpload: ['./**/*.map']` so the maps are not public. Keep the upload token in CI secrets, never in the repo.
- **PDPL** (the Saudi personal-data law): error reports can carry owner names, phones and medical notes.
  - Set `sendDefaultPii: false` explicitly.
  - Strip `event.user`, request bodies and breadcrumb data in `beforeSend` / `beforeBreadcrumb`.
  - Don't enable Session Replay.
  - Use ids, never names, in error messages.
- SDAIA (the Saudi data authority) published a **draft PDPL amendment** (consultation 6 Oct – 5 Nov 2026) that proposes storing personal data in the Kingdom. If it passes, every non-KSA processor matters, including the Supabase project region itself.
- Sources: https://sentry.io/pricing/ · https://docs.sentry.io/organization/data-storage-location/ · https://docs.sentry.io/platforms/javascript/guides/react/sourcemaps/uploading/vite/ · https://docs.sentry.io/platforms/javascript/data-management/sensitive-data/ · https://supabase.com/docs/guides/functions/examples/sentry-monitoring · https://github.com/getsentry/sentry-javascript/issues/15229 · https://betterstack.com/error-tracking · https://www.clydeco.com/en/insights/2026/10/sdaia-publishes-draft-amendments-to-the-pdpl

**Recommendation (D):**
- When Touq is first hosted for a pilot clinic, add **Sentry on the free plan, EU region**, with a strict `beforeSend` scrubber and no replay. That is about 30 lines.
- If the in-Kingdom storage rule becomes law, point the same SDK at a self-hosted **GlitchTip** on a KSA server. Only the DSN changes.
- Watch the SDAIA draft. It may also decide where Supabase itself may live.
