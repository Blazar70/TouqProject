## 3. Bugs (new)

**B33 — Low — The server lets the admin purge a clinic that was never put in the trash**
- Where: `supabase/functions/admin-manage-clinic/index.ts:250-258`. The `purge` action calls `purgeClinic()` without checking `deleted_at`.
- Scenario: the design is two-stage: trash (which can be undone) first, then purge (which can't). The screen only shows **Purge now** for trashed clinics (`AdminPage.tsx:1736-1767`), so this is safe today. But any future button, script or mistyped id that calls `purge` on a live clinic wipes it at once: its pets, visits, invoices and staff accounts. The 7-day safety window never applies. A single "OK" in a confirm box is the only guard (see H51).
- Fix (S): before purging, `select name, deleted_at` and return a 409 error ("trash the clinic first") when `deleted_at` is null.

**B34 — Low — One failed pet purge stops every clinic purge, and photos past the first 1,000 records are never deleted**
- Where: same file, `:281` (`if (petError) return jsonError(...)` comes before the clinic loop at `:293`), and `:273`/`:278`. Those two lines read photo paths with no `.limit()`/paging, so Supabase's 1,000-row cap applies (the same cap as B29).
- Scenario 1: one trashed pet can't be deleted, for example because of a new foreign key (a link from another table) that doesn't cascade. Then the nightly job returns 500 before it reaches the trashed clinics, and keeps doing so every night. Clinics trashed more than 7 days ago are never purged, and the cron job (the scheduled database task) shows only a generic failure.
- Scenario 2: a big clean-up trashes pets that together have more than 1,000 visit records with photos. The pet rows are deleted (records cascade with them), but only the first 1,000 photo paths were read, so the rest stay in `pet-photos` with nothing pointing to them. That is personal data kept after deletion, which matters under PDPL (Saudi Arabia's personal data law).
- Fix (S): record the pet error in the response and carry on to the clinics. Read the paths page by page (`.range()`), as `removeFolder` already does for storage.

I also checked, and found sound: every table that refers to a clinic without `on delete cascade` (meaning its rows are not removed automatically with the clinic) is either deleted by `purgeClinic` or is removed automatically with a parent row it does delete. So, as of 0102, a clinic purge does not stop partway through on a foreign key.

## 4. Security (new)

- **Print windows (`PrintContext.tsx`):** every value typed by staff or stored in the database goes through `escapeHtml` before it is written into the print document. That covers names, notes, prescription lines, waiver text, report cells, logo and photo URLs, and invoice lines. This stops XSS, where someone types code into a field and it runs in another user's browser. The only values written without escaping are numbers (`pet_number`, quantities), translation strings the app itself ships, and the QR code's Base64 text, which can't contain quotes. Verdict: no XSS.
- **`admin-manage-clinic`:** the caller must be a non-disabled `admin`, checked through the service-role client (the server-side client with full database access). The cron caller is accepted only with `x-cron-secret`, and it can run only `purge_expired`. If the secret isn't set, the comparison is against `undefined` and fails safely. Clinic data is read only through ids taken from the request after the admin check.
- No new security issues tonight.

## 6. HCI / visual / usability ideas

**H49 — Pick a free time with one tap when booking** (M)
- Problem: booking a time takes three dropdowns: hour, minute and AM/PM (`AppointmentsPage.tsx:1254-1282`). Staff only find out about a double booking after pressing Save (the conflict box at `:1312`). On an iPad, each dropdown opens a wheel picker, so one booking means 6+ taps.
- Who: receptionists, all day long.
- Change: once a date and doctor are chosen, show a row of chips (small tap buttons) for that doctor's free 15-minute slots, using the appointments and time-off data the page already loads. One tap fills all three selects. Keep the selects for unusual times. Note that appointments are fixed at 30 minutes until `duration_minutes` exists (`:82`).

**H50 — Resize photos in the browser before upload** (S)
- Problem: `validateImageFile` turns down anything over 5 MB (`src/lib/imageUpload.ts:3-13`). Photos from newer phones, and X-ray exports saved as PNG, often go over that. Files under the limit are uploaded at full size, which is slow on clinic Wi-Fi and fills storage.
- Who: doctors and nurses adding visit or inpatient photos (`SessionPage.tsx:448`, `PetDetail.tsx:634`, `InpatientPanel.tsx:165`).
- Change: in `uploadPhoto`, draw the image with `createImageBitmap`, scale its long side down to about 2000 px, and save it with `canvas.toBlob(..., 'image/jpeg', 0.85)`. This uses only browser features, with no new dependency. Run the size check after resizing. Skip resizing for videos and GIFs. Add one small test for the scaling maths.

**H51 — Type the clinic's name to confirm a purge** (S)
- Problem: purging a clinic can't be undone, and today the only guard is a normal confirm box (`AdminPage.tsx:391`), the same one used for small actions. Pressing Enter by reflex wipes a clinic.
- Who: the platform admin.
- Change: in the purge confirm, add a text box that keeps the red button disabled until the clinic's name is typed exactly. This is the pattern GitHub and Supabase use for deleting things. It pairs with the server check in B33.

**H52 — Reminders: "Send next" for working through the list** (S)
- Problem: the reminders page (`RemindersPage.tsx:200-241`) is a list of separate WhatsApp buttons. After each send, the receptionist comes back from WhatsApp and has to find their place again, and with 20+ reminders a day that is easy to lose.
- Who: receptionists every morning.
- Change: after a send, scroll to the next unsent item and highlight it, and show "7 of 12 sent" at the top. Each item already has its sent/skipped state, so this is mostly a counter plus `scrollIntoView` (a browser call that scrolls an element into view).

### U) Testing migrations automatically

Touq already has the pieces: `scripts/rebuild-db.mjs` applies every migration in order to an empty database, and `.github/workflows/checks.yml` runs on every push to `main`. What's missing is a database to aim the script at.

| Option | What it is | Price (seen 2026-11-01) | Fit for Touq | Effort | Risk |
|---|---|---|---|---|---|
| **Supabase CLI in GitHub Actions** (`supabase/setup-cli`, then `supabase start` or `supabase db start`) | Starts the full local Supabase stack in Docker on GitHub's machine, including the `auth`, `storage`, `vault`, `pg_cron` and `pg_net` that the migrations use | Free (included in GitHub Actions minutes) | Run `node scripts/rebuild-db.mjs --apply` with `DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres`, then the `supabase/tests/*_check.sql` files that don't need staging secrets. It needs a CI-only `supabase init`, which doesn't conflict with the "no local Supabase project" rule because nothing gets committed | **S–M** | The local stack's Postgres version can lag the hosted one by a little. Tests that read Vault secrets (0077, 0079) must be skipped or given dummy secrets |
| pgTAP + `supabase test db` | Supabase's official way to write database tests (pgTAP is a unit-test add-on for Postgres) | Free | Touq's checks are plain `assert` blocks, which already work with `psql`, so rewriting them in pgTAP isn't needed | M | None |
| Supabase Branching | A temporary hosted copy of the project for each Git branch | About **$0.01344 per branch per hour** (about $0.32/day on Micro). Pro plan compute credits don't apply | Tests the real hosted platform, but needs a Pro project linked to GitHub, and Touq works only on `main` | M | Costs money, and it ties CI to the Supabase GitHub integration |
| Neon branching | Postgres branches from another vendor | 10 branches included on paid plans | Not Supabase: no `auth`/`storage` schemas, so most migrations fail | — | Not a fit |

**Recommendation (U):** add a second job to `checks.yml`: checkout → `supabase/setup-cli` → `supabase init` + `supabase start` → `node scripts/rebuild-db.mjs --apply` → run the self-contained check files with `psql -v ON_ERROR_STOP=1`. Expect about 3–5 minutes per push. That turns "run the migrations on a fresh project" into a red or green signal on every push. The backup drill (a real `pg_dump`/restore of staging) remains a separate, manual step.

### V) X-rays and other medical images

Today Touq stores photos as JPEG/PNG/WebP/HEIC up to 5 MB (0055), in private buckets, behind signed URLs (links that expire after a set time). Vet X-ray machines produce **DICOM** files (the medical imaging standard, often 10–50 MB, with patient data inside the file).

| Option | What it is | Price (seen 2026-11-01) | Fit for Touq | Effort | Risk |
|---|---|---|---|---|---|
| **Keep JPEG exports + resize in the browser (H50)** | The clinic exports a JPEG from the X-ray software, and Touq attaches it to the visit like a photo | Free | Enough for "show the owner" and "remember what we saw". Diagnosis still happens on the X-ray workstation | **S** | Lower image quality, which is fine because it isn't used for diagnosis |
| Supabase Storage image transformations | Resizes images on the server, on request | Pro: 100 origin images per month included, then **$5 per 1,000** | Gives thumbnails without changing upload code, but costs grow with use, and H50 does the same job for free | S | Small cost, Supabase-only |
| Cornerstone3D / OHIF Viewer | Open-source (MIT licence) libraries for viewing DICOM in the browser, with zoom, window/level and measurements | Free | Would let doctors view DICOM inside Touq. The bundle is large (WebGL plus WASM, compiled code that runs in the browser) and needs a DICOMweb server (a server that serves DICOM files over the web) | **L** | Big maintenance load for one feature |
| DWV (DICOM Web Viewer) | A lighter DICOM viewer library | Free, **GPL-3.0** | Its licence would require publishing Touq's code if Touq ships it; the project says it is "not for diagnostic use" | M | Licence risk |
| Vet cloud PACS (an image archive system, e.g. PostDICOM, Asteris, iQ-4CLOUD VET, Vetology) | Hosted DICOM storage and viewer, with optional teleradiology (remote specialist reads) | Quote or tiered by storage. No public monthly prices found | The clinic keeps its own PACS, and Touq stores only a link to the study | S (link field) | Saudi data hosting is unclear (PDPL, see G) |

**Recommendation (V):** for v2/v3, don't handle DICOM. Do H50, and add an optional "Imaging link" field on the visit record later, for clinics that already have a PACS. Revisit Cornerstone3D only if several clinics ask to view X-rays inside Touq.
