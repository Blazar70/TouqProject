## 3. Bugs (new)

**B1 — Medium — An "In session" appointment can never be cancelled, rescheduled or undone**
- `src/pages/SessionPage.tsx:80-86` moves the appointment to `in_session` the moment the session page *opens*. `src/pages/AppointmentsPage.tsx:698-729` then shows only **Resume** and **Close** for `in_session`; Cancel/Reschedule exist only for `requested`/`confirmed`.
- Scenario: a receptionist-doctor taps *Start session* on the wrong pet, or the owner leaves before the exam. The card stays "In session" forever; the only way out is *Finish*, which requires visit type + diagnosis + treatment, i.e. a fake medical record.
- Fix: show Cancel (with reason) for `in_session` too, and add a "Back to confirmed" action that clears `started_at`. Optionally only auto-start when the user presses a button on the session page, not on page load.

**B2 — Low — Finishing a visit marks it completed before the medical record is saved**
- `src/pages/SessionPage.tsx:153-187`: status → `completed` first, then `medical_records.insert`. If the insert fails (network drop, RLS error) and the doctor closes the tab, the appointment is "completed" with no record (the panel then says "No record").
- Fix: insert the record first, then set status; or do both in one Postgres function (RPC = a database function the app calls) so they succeed or fail together.

**B3 — Low — Invoice header and its line items are two separate writes**
- `src/pages/PaymentsPage.tsx:186-222`: the invoice is inserted, then `invoice_items`. If the second call fails, only a toast appears and the form resets; an invoice with a total but no items stays in the ledger. Also `amount_total` is the float sum of unrounded `unitPrice × quantity` while each `line_total` is rounded separately by Postgres, so they can differ by 1 halala.
- Fix: one RPC `create_invoice(items jsonb)` that inserts both in a transaction and computes totals in SQL with `round(..., 2)`.

**B4 — Low — Times follow the device's clock, not the clinic's time zone**
- No code uses `Asia/Riyadh` or `clinics.timezone` (grep for `timeZone`/`Riyadh` in `src/` finds nothing). `format.ts`, the dashboard "today" range (`DashboardPage.tsx:52-55`) and Payments "today" totals (`PaymentsPage.tsx:303-304`) all use the browser's local time.
- Scenario: the platform admin travelling (or a tablet with the wrong zone) sees appointments shifted by hours and "today" totals for the wrong day.
- Fix: pass `timeZone: 'Asia/Riyadh'` (or the clinic's `timezone`) to every `Intl.DateTimeFormat` in `src/lib/format.ts`; build day ranges with that zone.

**B5 — Low — Push text is English-only and shows the raw status code**
- `supabase/functions/notify-status-change/index.ts:53`: body is `` `${pet}'s appointment is now ${appointment.status}.` `` → "Bella's appointment is now in_session." for Arabic-speaking staff too.
- Fix: keep a small EN/AR status label map in the function and store each profile's language (or send both lines).

## 4. Security (new)

**S1 — Medium — Disabled ("removed") staff keep receiving push notifications with pet names**
- `notify-status-change/index.ts:40-48` selects every profile of the clinic and `send-appointment-reminders/index.ts:15-19` every profile with a lead time; neither filters `disabled = false` (or a disabled clinic), and disabling a staff member (`clinic-manage-staff` `set_disabled`) does not delete their `push_subscriptions`.
- Scenario: a manager removes a nurse who quit; the nurse's phone keeps showing "Reminder: Bella's appointment is coming up" for that clinic. Data shown to someone who should no longer see it.
- Fix: add `.eq('disabled', false)` (and join `clinics.disabled = false`) in both functions, and delete the user's `push_subscriptions` inside `set_disabled`.

**S2 — Medium — Any staff role can edit or delete paid invoices, with no audit trail**
- RLS `invoices_all_vet` / `invoice_items_all_vet` (`0037_service_payments.sql:67-78`) is `for all` by clinic only — clinic roles are not used yet. The UI lets anyone verify-and-change `amount_total`/`paid_at` (`PaymentsPage.tsx:241-256`) and hard-delete an invoice (`:274`). Nothing is written to `admin_audit_log`.
- Scenario: a receptionist records 500 SAR cash, later edits it to 300 SAR or deletes it; the manager's totals change and there is no record of who did it. For ZATCA, issued invoices must not be deleted — corrections go through credit notes.
- Fix (phase 4 roles): limit delete/update to managers, replace hard delete with a `voided_at` + reason, and log changes with a trigger.

**S3 — Low — Reminder edge function has no caller check**
- `send-appointment-reminders/index.ts:11` accepts any request. With Supabase's default JWT check, the public anon key (shipped in the app bundle) is enough to call it. Impact is small (it only sends reminders that are due, once each) but it is free load for anyone.
- Fix: require a `x-cron-secret` header like `admin-manage-clinic` does.

**S4 — Low — Public `clinic-logos` bucket accepts any file type and size**
- `0053_clinic_logo.sql:10-11` creates the bucket without `allowed_mime_types` / `file_size_limit`; the 5 MB / `image/*` check is client-only (`src/lib/imageUpload.ts:9-13`), and `image/*` includes SVG, which can carry script. Only admins and managers can write, so risk is low, but a public bucket can host arbitrary files under your domain.
- Fix: new migration `update storage.buckets set allowed_mime_types = '{image/png,image/jpeg,image/webp}', file_size_limit = 5242880 where id = 'clinic-logos';` (same for `pet-photos`).

**S5 — Low — "Purge clinic" leaves the clinic's photos in storage**
- `admin-manage-clinic/index.ts:72-99` deletes rows and auth users but never removes files under `<clinicId>/` in `pet-photos` (pets and medical-record photos) or `clinic-logos`. After an "irreversible" purge, pet photos remain. Under Saudi PDPL (personal data law), deleted data should actually be deleted.
- Fix: in `purgeClinic`, list and remove `storage.from('pet-photos').list(clinicId, …)` recursively, plus the logo, before deleting the clinic row.

### A) ZATCA e-invoicing

ZATCA is the Saudi tax authority. Fatoora is its e-invoicing system.

**Where Touq stands today:** nothing in `src/` or `supabase/` holds a clinic VAT number, a QR code or any ZATCA field. Searching for `vat_number`, `qr`, `tlv` and `zatca` finds nothing.

**Phase 1 ("generation"), which applies now to every VAT-registered seller**
- A simplified (B2C) invoice needs a QR code. The QR holds five TLV fields encoded in Base64: seller name, VAT number, timestamp, total including VAT, and VAT amount.
- TLV means tag, length, value. The length is counted in bytes, so an Arabic name must be measured in UTF-8.
- Sources disagree on the exact timestamp format (unverified).
- This is a small pure function and needs no provider.
- Sources: https://zatca.gov.sa/en/RulesRegulations/Taxes/Documents/E-invoicing_Simplified%20GL.pdf, https://www.wafeq.com/en-sa/tax-and-reporting/qr-code-requirements-for-e-invoices-zatca-saudi-arabia, https://www.qoyod.com/en/learn/tlv-encoding-qr/

**Phase 2 ("integration")**
- Each invoice becomes UBL 2.1 XML with:
  - a UUID
  - an invoice counter (ICV)
  - the previous invoice's hash (PIH), which chains the invoices together
  - a cryptographic stamp from a certificate (CSID) issued to each invoicing unit (EGS)
- The QR code gets extra tags.
- B2B invoices must be cleared by ZATCA before they are sent. B2C "simplified" invoices, which are most vet visits, are signed by the seller and reported within 24 hours.
- Source: https://www.cleartax.com/ksa/e-invoicing-clearance-reporting-ksa

**Deadlines**
- Wave 24 (revenue above SAR 375k) was due 2026-06-30.
- **Wave 25 was announced 2026-07-24.** It covers taxable revenue above **SAR 187,500** in any year from 2022 to 2025, with integration due **2027-02-01**. That is about SAR 15.6k a month, so almost any VAT-registered clinic is covered.
- ZATCA notifies the taxpayers it selects. Penalties of SAR 5k–50k are reported by a vendor (unverified).
- Sources: https://zatca.gov.sa/en/MediaCenter/News/Pages/Wave25-E-invoicing.aspx, https://kpmg.com/us/en/taxnewsflash/news/2026/07/saudi-arabia-e-invoicing-mandatory-for-taxpayers-with-revenue-above-sar-187500.html

**Options compared**

**Recommendation (A)**
1. Add `clinics.vat_number` and a Phase 1 QR to the receipt from idea H2 now. It is cheap and it is the law today.
2. Make invoices append-only, voiding with a reason instead of deleting (S2), and reserve columns for `uuid`, `icv`, `previous_hash`, `zatca_status` and the signed XML. Phase 2 then becomes an addition, not a rewrite.
3. Don't build the Phase 2 signing chain until a real clinic with a VAT number exists. At that point, prefer sending invoices to the clinic's own accounting provider (Wafeq or Qoyod), which keeps the compliance liability off Touq. Keep `zatca-xml-ts` plus the ZATCA SDK as the self-built fallback.

### B) Owner appointment reminders: WhatsApp and SMS in KSA

**SMS sender rules (CST)**
- CST is the Saudi telecom regulator. Every SMS sender name must be pre-registered.
- Registration needs: a CR (commercial registration), an Arabic authorisation letter, the signer's ID, and VAT/Zakat certificates.
- It takes about 20 business days and costs about $65/year per sender (2024 vendor figures, unverified for 2026).
- Promotional senders need the "-AD" suffix, and Mobily has blocked promotional senders since April 2024. Reminders count as transactional, so they are fine.
- Sources: https://docs.unifonic.com/articles/products-documentation/ksa-sender-id-registration-requirmnets, https://d7networks.com/sms/saudi-arabia/sms-regulations/

**WhatsApp pricing**
- Since 2025-07-01, WhatsApp bills per message. "Utility" templates, such as reminders, are free only within 24 hours of the customer's last message. A reminder sent the day before is normally billed.
- Saudi utility rate is **about SAR 0.04 ($0.0107) per message**. This comes from vendor rate cards, not Meta's own card (unverified). Meta added SAR billing and raised the Saudi marketing rate on 2026-04-01.
- Source: https://developers.facebook.com/docs/whatsapp/pricing

| Provider | Channel | Price (seen 2026-10-21) | Effort from a Deno edge function | Risks / lock-in |
|---|---|---|---|---|
| Meta WhatsApp Cloud API (direct) | WhatsApp | Meta's rate only, about SAR 0.04 per utility message | **S**: one `fetch` POST to `graph.facebook.com/.../messages`; templates take 24–48h to approve | Meta business verification; template rejections; no SMS fallback. Low lock-in |
| Unifonic (Saudi) | SMS + WhatsApp (official BSP, a Meta-approved reseller) | Not published; SMS is charged on submit even if not delivered | **S–M** | Medium: the sender registration is tied to Unifonic |
| Taqnyat (Saudi) | SMS (WhatsApp offering unverified) | Not found; the API returns the cost in SAR | **S**: `POST api.taqnyat.sa/v1/messages`, 100 calls/min | Low–medium |
| Twilio | SMS + WhatsApp | KSA SMS **$0.1949 per segment**. An Arabic segment is only 70 characters, so a reminder may use 2 segments | **S**: best docs | The most expensive by far |

Sources: https://developers.facebook.com/documentation/business-messaging/whatsapp/get-started, https://docs.unifonic.com/docs/how-sms-is-charged-by-unifonic, https://learn.microsoft.com/en-us/connectors/taqnyat/, https://www.twilio.com/en-us/sms/pricing/sa

**Recommendation (B)**
1. Keep web push as the free channel for staff.
2. For pet owners, add **Meta WhatsApp Cloud API directly**. It is the cheapest option found, it is one `fetch` from the existing `send-appointment-reminders` function, there is no middleman, and Arabic templates are supported. You need to store owner consent and an opt-out flag on `pets` (PDPL).
3. Add SMS only if owners without WhatsApp turn out to matter. In that case, get quotes from Taqnyat and Unifonic before considering Twilio.
4. Start the paperwork early: Meta business verification, plus a CST sender ID if SMS is used. It takes weeks, and no code can speed it up.
