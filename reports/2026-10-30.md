## 3. Bugs (new)

**B29 — High — Lists stop at 1,000 rows without saying so, so pets and owners beyond that can't be found or billed**
- Where: each of these loads the whole list in one request with no `.range()` (paging): `PetsPage.tsx:50` and `:65` (pets, newest first), `AppointmentsPage.tsx:236` (pets for the booking picker, A–Z), `PaymentsPage.tsx:121` (pets for the payment picker, A–Z), `OwnersPage.tsx:28` and `OwnerPickerModal.tsx:41-44` (owner files, A–Z). Search then filters only that downloaded list in the browser (`matchesPetSearch`, `matchesOwner`).
- Why: Supabase's API (PostgREST, the layer that turns `supabase.from(...)` into SQL) returns **at most 1,000 rows by default** ("Max rows" in the project's API settings). Going over the cap is not an error: the request "succeeds" with the first 1,000 rows. RLS (row-level security) limits each list to one clinic, so the trouble starts at 1,000 pets *per clinic*. The admin import (0097/0098) accepts 5,000 rows per file.
- Scenario: a clinic is onboarded with 3,000 pets. Reception books "Zaid's cat Yasmin". The booking picker only holds pets A to about H, so Yasmin isn't there. Reception registers her again and creates a duplicate pet. In Owners, every owner after roughly the 1,000th name is missing, so `OwnerPickerModal` makes a duplicate owner file too. Payments can't find the pet to bill. On Pets (newest first), the *oldest* 2,000 pets disappear. Every visit to these pages also downloads up to 1,000 full pet rows (`select('*')`), which is slow on a clinic tablet.
- Fix (M): search on the server. When the user types, query with `.or('name.ilike.%q%,owner_phone.ilike.%q%')` (plus the pet number) and `.limit(50)`, the way `AdminPage.tsx:209` already does. Show "the 50 most recent" when the box is empty. Stopgap (S, today): raise "Max rows" in the Supabase dashboard (e.g. to 10,000). Also make each list warn "showing first N" when `data.length` equals the cap, so this never fails silently again.

**B28 — Low — The idle "save before sign-out" still loses the record in three cases**
- Where: `IdleLogout.tsx:28-31` and `:60-66`, and `idleLogout.ts:17` (`idleGuards` is a plain variable in each tab).
- (1) **Two tabs.** A doctor has the visit form open in tab B and the dashboard in tab A. Tab A has no unsaved form, so it uses the 10-minute limit and calls `signOut({ scope: 'local' })`. That clears the shared sign-in, and supabase-js tells tab B, which signs out too. Tab B's saver never runs and its 60-minute limit never applies. This is common on reception PCs. The installed PWA on a tablet has one window, so tablets are not affected.
- (2) **Vitals that don't parse.** `saveRecord()` returns `null` when a vital sign doesn't parse (e.g. a stray letter in the temperature box, `SessionPage.tsx:168-172`). `idleSignOut` ignores the result and signs out anyway, so everything is lost, not just the bad field.
- (3) **Pet file edits** (`PetDetail.tsx`) count as unsaved, so the limit becomes 60 minutes, but no saver is registered for them, so the edits are still dropped at minute 60.
- Fix (S): keep the "unsaved form" count in `localStorage` (as `touq.lastActive` already is), so every tab applies the longer limit. In `idleSignOut`, skip the sign-out (or extend the timer) if any saver returns `null`. For (3), accept it and note it, or register a saver there too.

That is rare and visible in the count.

## 6. HCI / visual / usability ideas

**H39 — Search-as-you-type that finds any pet in the clinic** (M, goes with B29)
- Problem: the pickers in booking and payments show one long A–Z list that already lives in memory. With thousands of pets that list is slow to scroll on a tablet, and it is incomplete (B29).
- Who: receptionists, many times a day.
- Change: when the box is empty, show "Recent" (pets seen in the last 7 days, about 20). Each keystroke (with a 250 ms debounce, meaning wait until typing pauses) queries the server by name, phone or pet number. Normalize Arabic on both sides (أ/إ/آ → ا, ة → ه, ى → ي, strip tashkeel, the short vowel marks) so "احمد" finds "أحمد". `toLatinDigits` already handles Arabic-Indic digits. Where: `PetPicker.tsx`, the booking pet search in `AppointmentsPage.tsx`, `OwnerPickerModal.tsx`. See research Q for the database side.

**H40 — Don't flag normal puppy and kitten growth as an alarm** (S)
- Problem: the new red "+25% since the last weighing" (`WeightChart.tsx:36-38`) fires at every vaccine visit for a growing puppy, which gains 10–30% between visits. Red that is usually noise teaches doctors to ignore it, including a real 12% loss in an old cat.
- Who: doctors reading the pet file.
- Change: pass `date_of_birth` into `WeightChart`. Flag only *losses* over 10% for pets under 12 months (or unknown age with a short history), and keep the ±10% rule for adults. Also show the change as kg, not just %, e.g. "−0.6 kg (−12%)".

**H41 — Autosave the visit record while typing, with "Saved 10:42"** (S–M)
- Problem: the record is only written on "Save" or "Finish", or now just before an idle sign-out. A browser crash, an iPad killing the PWA in the background, or a dead battery still loses everything. Doctors can't see whether they've saved.
- Who: doctors and nurses during visits.
- Change: in `SessionPage.tsx`, call the existing `saveRecord()` 5 seconds after the last change while the form is dirty and the vitals parse. Show a quiet status line under the form: "Saving…", then "Saved 10:42", or "Not saved: check temperature". This also removes most of B28. The field-level merge already prevents overwriting the other person's fields.

**H42 — Microchip number on the pet file** (S–M)
- Problem: Touq has no microchip field (`grep microchip` finds nothing). Imported pets and travel pets need an ISO 11784/11785 chip (15 digits) for rabies certificates and import papers. Lost pets are identified by scanning it.
- Who: doctors (vaccination and travel certificates), receptionists (identifying a found pet).
- Change: a nullable `pets.microchip` column with a 9/10/15-digit check, shown and printed with `<Ltr>`. Add it to the pet search (H39) and the import columns (`csvImport.ts`). Handheld USB scanners type the number like a keyboard, so a plain input with `inputMode="numeric"` works. See research R.

**H43 — Say which rows were "already there" after an import** (S)
- Problem: the toast says only "N skipped" (`AdminImportModal.tsx:38`). The admin can't tell whether those were true repeats or two different pets merged (the same-name case in section 4).
- Change: return the skipped row numbers from `admin_import_owners_pets` (it already counts them). Offer "Download skipped rows (CSV)" using `downloadCsv`, which is already imported in that file.

### Q) Searching thousands of pets and owners, in Arabic and English

| Option | What it is | Price (seen 2026-10-30) | Saudi / Arabic fit | Effort with React + Supabase | Risk / lock-in |
|---|---|---|---|---|---|
| **Postgres `ilike` + `pg_trgm`** (trigram = 3-letter chunks) | Built into Supabase. | **PGroonga** (Supabase extension) | Full-text index for all languages. Supabase's docs say native Postgres full-text search is limited to alphabet-and-digit languages | Free extension | Built for CJK and Arabic-style scripts | M: new operators (`&@~`), needs an RPC (database function) | Less common; check the version Supabase ships |
| **Meilisearch Cloud** | Hosted search engine, typo-tolerant, good Arabic support per comparisons | About $23–30/month entry (sources disagree), 14-day trial, free self-hosted | Good | **L**: sync every pet and owner change through an edge function or webhook, plus RLS-equivalent per-clinic filtering via signed tenant tokens | Second copy of personal data outside Supabase, so a PDPL processor agreement is needed (see G) |

| Algolia | Hosted search, free Build tier (around 10K searches/month), then pay per use | $0.50 per 1K searches on Grow | Fine | L | Most lock-in; data in the US/EU |

**Recommendation (Q):** use **Postgres with `pg_trgm` and an Arabic normalization function**. At clinic scale (thousands to tens of thousands of rows per clinic) it is fast, costs nothing, keeps RLS doing the per-clinic separation, and keeps personal data in one place. Don't add an external search engine. It would mean a second copy of owner phone numbers to protect under PDPL, and a sync job to maintain. Look at PGroonga only if trigram matching proves too fuzzy for Arabic.

### R) Microchip identification

- **What I found:** dogs and cats entering KSA need an ISO 11784/11785 microchip implanted *before* the rabies vaccine. The import permit goes through MEWA (Ministry of Environment, Water and Agriculture) via the Naama portal, according to travel guides; I found no primary MEWA page. I found **no national domestic pet microchip registry or API** in Saudi Arabia. KAUST runs its own community pet registration. Abu Dhabi (UAE) has a mandatory registry (TAMM), but that is not KSA.
- **Lookups:** the AAHA Universal Pet Microchip Lookup (US) only checks which *participating* registries know a chip. It stores no data, has no public API, and is aimed at US chips.
- **Why it matters for Touq:** certificates for travel and import, and identifying found pets inside the clinic's own records. There's nothing to integrate yet, but storing and searching the number (H42) is cheap and expected by clinics.

**Recommendation (R):** add the field (H42), print it on vaccination and travel paperwork, and recheck MEWA every few months for a national registry. Don't build any external lookup now.
