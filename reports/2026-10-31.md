## 3. Bugs (new)

**B31 — Medium — The pet picker can select the wrong pet when Enter is pressed quickly (microchip scanners do this every time)**
- Where: `src/components/PetPicker.tsx:68` (`matches = searching && found ? found.pets : []`) and `:83-86` (Enter picks `matches[active]`).
- Why: results arrive 250 ms after typing stops, plus the network round trip. Until then `found` still holds the *previous* list: the "Recent" pets if the box was empty, or the results for the earlier, shorter text. The code never checks that `found.query` matches the current `query`. `QuickSearch.tsx:52` does check it (`found.query === query`).
- Scenario: a receptionist opens booking and scans a microchip. USB scanners type the 15 digits and then press Enter within about 50 ms. The list still shows "Recent" pets, so Enter selects the newest pet in the clinic, not the scanned one. A fast typist doing "Luna" + Enter hits the same problem. The input then shows the wrong pet's label, which is easy to miss, and the wrong pet gets booked or billed.
- Fix (S): `const matches = searching && found?.query === query ? found.pets : []`, so Enter does nothing until the matching results arrive. Optionally run the search immediately when the text looks like a microchip or pet number.

**B30 — Low (Medium once invoices are real) — Reprinted tax invoices use the clinic's current VAT number, not the one they were issued with**
- Where: `InvoiceDetail.tsx:101-102` + `:208/:238` (`vatNumber` prop = `clinic?.vat_number`, `PaymentsPage.tsx:866`). `PrintContext.tsx:331` treats "no VAT number" as a plain invoice with no QR code. 0100 saves `tax_phase` on each invoice, but not `vat_number`.
- Scenario 1: the admin moves a clinic from phase 1 back to "not registered" and clears the VAT number (allowed: `AdminPage.tsx:467` and the database check only require a number for phase 1). Every earlier *tax* invoice now reprints as a plain "Invoice" with no VAT lines and no QR code. Scenario 2: the admin corrects a typo in the number, and old invoices reprint with the new number. In both cases the copy no longer matches the invoice the owner received, which matters in a ZATCA audit.
- Fix (S): in a new migration, add `invoices.vat_number`, fill it in from the clinic in `invoices_take_tax_phase()` (only when `tax_phase = 'phase1'`), and copy the current number into existing phase-1 rows. Then print from `invoice.vat_number`. Credit notes print through the same path, so they are fixed too.

**B32 — Low — The pet picker hides search failures, so they look like "no such pet"**
- Where: `PetPicker.tsx:58` reads only `{ data, count }` and ignores `error`. When nothing matches, the list just doesn't open (`showList` is false).
- Scenario: the clinic Wi-Fi drops for a moment, or the request fails. The receptionist types the owner's name, sees nothing, decides the pet isn't registered, and registers a duplicate. This is the same harm B29 described, from a different cause. `OwnerPickerModal.tsx:51` already shows the error.
- Fix (S): keep the error in state and show a one-line "Couldn't search, try again", plus an explicit "No pet matches" row (see H44).

## 4. Security (new)

What I checked and found sound:
- **0102 request keys:** the four function bodies match their latest versions (0086, 0066, 0064, 0061) line for line, except for the added key. I compared them with a diff script. The lookup by repeated key is limited to the caller's clinic. Unique partial indexes stop two concurrent calls with the same key from both saving; the second gets a "duplicate" error, which `friendlyError` maps. No earlier migration revoked EXECUTE on these functions, so dropping and recreating them loses no permission limits. The app keeps one key until a save succeeds, then makes a new one (`requestKey.ts`; `renew()` is called only after success in all four places). Known limit: if the first attempt did save but the reply was lost, and staff *edit the form* before pressing Save again, the server returns the first result and the edit is dropped. That is rare, and the screen then shows the saved invoice.
- **0100 tax status:** the clinic guard now lets only the admin change `vat_number`/`tax_phase` (they are not in the managers' list). Both triggers are `security definer` with `search_path` set. Invoices for an unregistered clinic get VAT 0 on every line and on the total, whichever path calls `create_invoice`. Prices on screen (`SettingsPage.tsx:238`, `PaymentsPage.tsx:277`) match what the server charges (list price including the stored rate).
- **0101 search:** `search_norm` is `immutable` with an empty `search_path`, and the Arabic letter folding is the same in SQL and TypeScript (`search.ts`). `%`, `_` and `\` typed by staff are escaped, and the search uses `.ilike()` without `.or()`, so typed commas can't break the filter. `pets.owner_name/owner_phone` stay in sync with owner files (0063 trigger), so owner-name search finds their pets. Each list is still limited to one clinic by RLS.
- **Lock screen:** a 20 px blur over 75% background hides patient data, and `#root` is made `inert`, so keyboards and screen readers can't reach the app behind it. Unlocking signs in again with the same email. Note (accepted design): the lock is a browser-side screen. The sign-in itself stays valid behind it, so someone with developer tools could remove the overlay. That is fine for a shared desk, but don't describe it as a security control.
- **List cache (`lastSeen.ts`):** kept in memory only, keyed by user, and cleared on sign-out. Nothing is written to disk.

No new security issues tonight.

## 6. HCI / visual / usability ideas

**H44 — "No pet matches. Register new pet" right in the picker** (S)
- Problem: when nothing matches, the picker shows nothing at all (`PetPicker.tsx:69`). Staff can't tell "no match" from "still loading" from "failed" (B32).
- Who: receptionists, at booking and billing.
- Change: three visible states under the input: "Searching…", "No pet matches 'X'" with a **Register new pet** button that opens `/pets/new` with the text pre-filled as the name (or the phone, if it is digits), and "Couldn't search, try again". Where: `PetPicker.tsx`, plus a query parameter read in `RegisterPetPage.tsx`.

**H45 — Search with several words in any order** (S)
- Problem: `search_text` holds "pet name, owner name, phone…" as one string, and the search looks for the typed text exactly as written. "زيد ياسمين" (owner, then pet) finds nothing, but "ياسمين زيد" works. Arabic speakers often say the owner first.
- Who: everyone who searches (Pets, Owners, pickers, Ctrl+K).
- Change: split the query on spaces and chain one `.ilike('search_text', pattern)` per word. The query builder already adds conditions together (AND). Return an array from `searchPattern()` in `src/lib/search.ts` and loop over it at the 5 call sites. The trigram index still serves each condition.

**H46 — Warn about a microchip number that is already on another pet** (S)
- Problem: `pets.microchip` has a format check but isn't unique. A double scan or a re-registration creates two pets with the same chip, and the lost-pet lookup then shows two answers.
- Who: receptionists and doctors.
- Change: on blur of the microchip field (`RegisterPetPage.tsx:195`, `PetDetail.tsx`), run `select id, name, pet_number from pets where microchip = X`. Show "Already on Luna (#1234). Open?" as a warning, not a block (a transferred pet can be re-registered on purpose). Later, a unique partial index per clinic.

**H47 — A search button in the phone top bar, and no keyboard hint on touch** (S)
- Problem: on phones the top bar (`AppShell.tsx:188-200`) has only the menu button. Quick search lives inside the slide-out menu (`:259-275`), so it takes 2 taps, and it still shows a "Ctrl K" hint that means nothing on a touch screen. Tablets get it in the rail (1 tap), which is fine.
- Who: doctors and nurses using their phones on the ward or at the kennels.
- Change: a 44 px magnifier button at the end of `.app-topbar` that calls `setSearchOpen(true)`. Hide `.nav-kbd` with `@media (hover: none)`.

**H48 — Lock screen: show who locked it, and when** (S)
- Problem: at a shared reception desk, the next person sees "locked" but not since when or for which user, until they read the hint. Staff may type their own password into a colleague's lock.
- Change: show the avatar/name large, then "Locked at 10:42" (from `touq.lastActive`), and make **Not you? Sign out** the second button at equal size. Where: `IdleLogout.tsx:125-150`, `.lock-card` in `App.css`.

### S) Keeping the clinic working when the internet drops

| Option | What it is | Price (seen 2026-10-31) | Fit for Touq | Effort | Risk / lock-in |
|---|---|---|---|---|---|
| **Do more of what Touq already does** (autosave, request keys, a visible offline banner, a "retry" on failed saves) | No new service | Free | Covers short drops (seconds to minutes), the common case on clinic Wi-Fi | **S** | None |
| **Workbox Background Sync** (already in the build via `vite-plugin-pwa`) | The service worker (the PWA's background script) stores failed POSTs in IndexedDB (the browser's built-in database) and replays them later | Free | **Not supported on iOS/iPadOS Safari** (all versions through 26.5) or Firefox, and iPads are Touq's main tablets. A queued request also carries a sign-in token that expires after about 1 hour, so a late replay fails with a 4xx error and Workbox drops it silently | M | Silent data loss if misused. Not recommended for money or records |
| **PowerSync** | Sync engine: a local SQLite database in the browser stays in sync with Supabase Postgres, and writes made offline are queued and uploaded through your own code | Free tier. Pro about $49/month per comparison sites; open/self-hosted edition available | Works with Supabase JWTs. Read access is defined by PowerSync "sync rules", which **duplicate your RLS** (two places to keep correct). Writes still go through your RPCs, so 0102's request keys fit well | **L** (every list and form would read from local SQLite) | High. A second copy of patient and owner data on each device (PDPL: lost tablet, see G) |
| ElectricSQL | Postgres → client "shape" sync | Open source + cloud | Read-sync only; offline writes are your job. The product was mid-rewrite per comparisons | L | In flux |
| RxDB | Local-first JS database with replication plugins | Open core, paid premium plugins | Needs custom replication to Supabase | L | Medium |

**Recommendation (S):** don't adopt a sync engine for v2/v3. Touq's failure case is short Wi-Fi drops, which autosave and request keys now cover, and full offline would put a second copy of personal data on every tablet. Instead (S effort): (1) show a clear "Offline: changes will be saved when you're back" banner using `navigator.onLine` and the `online`/`offline` events. (2) Have the visit record's autosave retry when the `online` event fires. (3) Don't use Workbox Background Sync for writes (iPad has no support, and tokens expire). Revisit PowerSync only if a clinic needs a truly offline mode, such as field or farm visits.
