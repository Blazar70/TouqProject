## 3. Bugs (new)

**B12 — Medium — The "ready for pickup" reminder goes out for every discharge, including a pet that died**
- `RemindersPage.tsx:61-65` lists every stay discharged in the last 2 days as "ready for pickup". It builds `pickupMessage`, which says "… is ready to go home. You can pick them up at …" (`ownerReminders.ts:44-48`).
- A stay has no outcome field. Discharge is the only way to close one (`InpatientPanel.tsx:168-169`, `0081_inpatients.sql`).
- Scenario 1: a cat dies overnight in hospital. The doctor discharges the stay with the note "died 03:10". Next morning the receptionist works down the "to send" list, taps Send, and WhatsApp opens with "Your cat is ready to go home". One more tap sends it to a grieving owner.
- Scenario 2: the owner collects the pet first and the stay is discharged at handover. The list then asks reception to tell an owner who is already home.
- Fix: add `discharge_outcome text check (… in ('home', 'died', 'euthanised', 'transferred'))` in a new migration, ask for it in the discharge confirm, and list only `home`. Also offer "Picked up already" so an item can be cleared without sending.

**B13 — Low — The signature pad breaks after the tablet is rotated**
- `SignaturePad.tsx:21-33` sets the canvas size in pixels once, when it mounts. The CSS width is `100%` (`App.css:4521`). After a rotation the canvas is stretched, while `point()` still uses the new CSS position (`:37-40`), so the ink no longer lands under the finger.
- Scenario: the owner turns the tablet to landscape to sign. The line appears off to the side and squashed, and the stored PNG looks like a scribble.
- Fix: listen for resize (a `ResizeObserver`) and run the sizing code plus `clear()` again. Or fix the canvas to a set size such as 600×180 CSS px.

**B14 — Low — Marking a combined vaccine reminder "sent" can fail and say nothing**
- `markSent` (`RemindersPage.tsx:148-155`) inserts one row per due vaccine in a single insert. If a colleague has already marked one of them, the unique key fails the **whole** insert with `23505` (duplicate key), and that error is hidden on purpose.
- Scenario: Sara marks one of two vaccines for an owner as sent. A moment later Ali taps Send on the combined message. WhatsApp opens and Ali sends it, but nothing new is recorded, so the item stays "to send". Tomorrow someone sends the same message again.
- Fix: insert with `upsert(…, { onConflict: 'clinic_id,kind,item_key', ignoreDuplicates: true })` instead of a plain insert.

## 4. Security (new)

**S11 — Medium — Receptionists (and managers) can edit or delete medical visit records**
- The database rule for `medical_records` is still `for all` by clinic only (`0001_init.sql:210-211`). The 0075 trigger limits **nurses** only (`enforce_medical_record_roles`). For any other role it just sets `vet_id := auth.uid()` on insert and lets edits and deletes through.
- The UI shows Edit and Delete to every staff account: `isVet = profile?.role === 'vet'` (`PetDetail.tsx:61`, buttons at `:563,568`). `role = 'vet'` is true for all staff, receptionists included.
- Scenario: a receptionist opens a pet file, taps Edit on last week's visit and changes the treatment, or deletes the record. Nothing logs the change. If a receptionist adds a record outside a session, `vet_id` is their own id, so the visit shows **them** as the doctor.
- Why it matters: a visit record is the clinical and legal history of the animal. Today the strictest rules apply to nurses, while receptionists have no limits.
- Fix: in `enforce_medical_record_roles`, raise for insert, update and delete unless `current_user_has_role(array['doctor','nurse'])`. Decide whether managers keep access. Hide the buttons with `isClinician` in `PetDetail.tsx`. Add a line to the 0075 check script.

**S12 — Low — Any staff member can delete inpatient photos and videos straight from storage**
- The `inpatient_updates` rule says only the author or a manager may delete an update (`0081:72`). The storage rule for the files lets anyone in the clinic delete them (`0081:131`, which checks only the clinic folder).
- Scenario: someone uses the API with their own login and removes the wound photos from an update about a complication. The update row stays, but its pictures are gone for good.
- Fix: drop the delete policy for staff and remove the files in the same place the row is deleted: a small `security definer` function, or the existing admin edge function. Or allow the delete only when the path is in an update the caller wrote.

### G) PDPL compliance

**Draft amendment** (consultation 6 Oct – 5 Nov 2026), from law-firm summaries:
- Draft Art. 23(2) would oblige controllers to store personal data inside Saudi Arabia, but transfers that follow the law would still be allowed. Reed Smith notes that the two parts contradict each other.
- The 72-hour breach notice would no longer depend on likely harm, so more breaches would have to be reported.
- Controllers that transfer data abroad would have to register.
- Consent for marketing messages would need proof.
- The changes would take effect 60 days after the final text is published in the official Gazette. No news since the early-October write-ups.

**What applies today** (in force since Sep 2024, fines up to SAR 5M). The clinic is the *controller* (the one who decides why data is collected) and Touq is the *processor* (the one who handles it for them).

| Duty | What Touq needs |
|---|---|
| Privacy notice | Bilingual: what is collected, why, who receives it, how long it is kept, and the owner's rights |
| Consent | Separate opt-in for marketing. Plain appointment and vaccine reminders can probably rest on "service", but promotional messages need consent. This affects the new WhatsApp reminders (0085) |
| Owner rights | Access, copy, correction and deletion, so Touq needs an export and a delete path per owner (`owner_files`) |
| Breach | Tell SDAIA within 72 h and the people affected without delay. Write the plan down now |
| Records of processing | A spreadsheet: purposes, data types, recipients, transfers abroad, how long data is kept |
| Transfers abroad | Hosting on Supabase outside KSA is a transfer. Use SDAIA's standard contract clauses (SCCs) plus a short risk assessment |
| Registration (National Data Governance Platform) | Free. Needed for some controllers; check whether the clinic or Touq meets a trigger |
| Processor contract | A data-processing agreement (DPA) with each clinic, and a list of Touq's own sub-processors (Supabase, Cloudflare, push services) |

Pet medical notes are about the animal, so they are probably *not* "health data" of a person. The owner's name, phone and any notes about the owner *are* personal data.
