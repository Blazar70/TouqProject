## 4. Security (new)

**S13 — Medium — "Delete owner data" (PDPL) leaves the owner's real name in the admin log**
- `anonymise_owner_file` (`0089_owner_anonymise.sql:26-38`) clears the name, phone, email and notes, and takes care to log only the anonymous label ("writing the real name here would keep it").
- But older log rows already hold the name in `admin_audit_log.target_label`:
  - balance top-ups and adjustments: `v_owner.name || ' · ' || amount …` (`0064_owner_balance.sql:143-146`)
  - owner merges: `v_remove.name || ' → ' || v_keep.name` (`0064:185-187`, `0088:83-86`)
- Scenario: an owner who once topped up a prepaid balance asks the clinic to delete their data. The manager taps "Delete owner data" and sees "deleted". The clinic's activity page (0080) and the admin log still show "Fatimah Al-… · 500.00 · cash".
- Why it matters: under PDPL the clinic has to erase the data, or have a legal reason to keep it. The function's comment shows the intent was to erase.
- Fix: in the same function, `update admin_audit_log set target_label = replace(target_label, v_owner.name, v_label) where clinic_id = v_owner.clinic_id and target_type = 'owner' and target_label like '%' || v_owner.name || '%'`. Better for later: log the owner's id rather than the name. Add one line to the 0089 check script.

## 6. HCI / visual / usability ideas

**H21 — No pre-chosen discharge outcome** (S)
- Problem: the discharge form starts with "Going home" selected (`InpatientPanel.tsx:61`, reset to `'home'` after each save). The worst mistake, telling a grieving owner to collect a pet that died, takes only two taps.
- Who: doctors discharging at the end of a long shift, and receptionists who then send the message.
- Change: start with `null`, so no radio button is selected and the Discharge button stays disabled until one is. Show "Died" and "Put to sleep" with a calm grey style, not the red delete style.

**H22 — "Next up" banner: give a single-patient day a proper empty state** (S)
- Problem: the WIP dashboard takes the next appointment out of the list (`DashboardPage.tsx:261`). When it is the only one left, the list below shows as an empty box with no text.
- Who: doctors on a quiet afternoon.
- Change: when the filtered list is empty, show "Nothing else today". Also give the banner `aria-label` text such as "Next up: Bella, 10:30, arrived", because screen readers read the parts as one run-on line.

**H23 — Ask before "Delete owner data", and say what stays** (S)
- Problem: the confirm only names the owner (`owners.deleteDataConfirm`). A manager can't tell that pets, visit history, invoices and signed waivers are kept, which is the right choice under PDPL and ZATCA. Next to "Export data" and "Add balance", it is also easy to tap by mistake.
- Who: clinic managers handling a deletion request.
- Change: use the confirm text to list "Deleted: name, phone, email, notes, trusted contacts. Kept by law: pets, visits, invoices, waivers". Ask the manager to type the owner's phone number before the button turns on. Suggest "Export first?" in the same dialog.

**H24 — Make "Bill this stay" warn when no hospital-night service is set** (S)
- Problem: if no service is marked as the hospital night, the bill opens with a line named "Hospital night", the right quantity and **no price** (`PaymentsPage.tsx:180-184`). A receptionist has to know the price.
- Who: receptionists billing a stay; managers who set up the price list.
- Change: when `night` is null, show an inline note "Set the hospital-night service in Settings → Price list" with a link. Managers get the link; others see "Ask a manager".

**H25 — Remember the chosen print size per device** (M, ties in with 7I)
- Problem: every print opens an 800×1000 pop-up with an A4 layout (`PrintContext.tsx:435,461`). Clinics with an 80 mm receipt printer at the front desk get a tiny strip, or waste A4 paper.
- Who: receptionists printing receipts all day.
- Change: a "Receipt printer: A4 / 80 mm" setting saved in `localStorage` per device, and a second `@page { size: 80mm auto; margin: 0 }` style in the print HTML. See 7I.

### I) Receipts and PDFs

What Touq has today: `PrintContext.tsx` builds an HTML page with the ZATCA phase-1 QR (`qrcode-generator`) and opens the browser's print dialog. In that dialog, "Save as PDF" already makes a correct PDF, with Arabic and RTL handled by the browser.

| Option | What it is | Price (seen 2026-10-26) | Arabic | Effort | Risk |
|---|---|---|---|---|---|
| Browser print, plus an 80 mm `@page` style | What Touq does now, plus a receipt layout | Free | ✅ the browser shapes it | S | Each device asks once for the printer; no silent printing |
| WebUSB / Web Bluetooth ESC/POS (e.g. `escpos-buffer`) | Sends printer commands straight from the page (ESC/POS is the command language of receipt printers) | Free (npm) | ❌ most receipt printers lack Arabic glyphs: you send a picture of the receipt instead | M–L | **Chrome/Edge only, no Safari**, so not on iPad. Different from printer to printer |
| `pdf-lib` in a Deno edge function | Draws a PDF on the server | Free | ❌ no Arabic shaping or bidi (right-to-left ordering): needs an extra shaper such as `bidi-shaper` and an embedded Arabic font | M | Silent wrong text, which is the worst kind of bug for a receipt |
| Gotenberg (self-hosted) | Docker service: headless Chromium turns HTML into PDF | Free, but it needs a server (about 1 GB RAM) | ✅ when an Arabic font is uploaded with the request or installed in the image | M | One more server to run, and Supabase can't host it |
| PDFShift (hosted HTML→PDF API) | POST the same HTML, get a PDF back | Free 50/month. "Boost" $24/month for 2,500, then $0.03 each | ✅ (Chromium) | S from an edge function | Owner data goes to another processor (PDPL: add it to the sub-processor list and DPA) |

Why it matters for Touq: owners will ask for the receipt on WhatsApp, and ZATCA phase 2 later needs a stored copy of each invoice. A PDF stored in Supabase storage, next to the invoice, covers both.

Sources: https://cdn.jsdelivr.net/npm/@maythiwat/escpos-buffer@4.0.4/README.md · https://pub.dev/packages/thermal_printer_flutter · https://app.unpkg.com/bidi-shaper@0.1.2/files/dist/render-BhplWt64.d.ts · https://computingforgeeks.com/gotenberg-html-to-pdf-api/ · https://blog.elest.io/self-host-gotenberg-a-pdf-rendering-api-for-your-apps-and-agents/ · https://pdfshift.io/faq · https://us.fitgap.com/products/pdfshift · https://wordpress.org/support/?p=18861607

**Recommendation (I):**
1. Now: keep browser printing and add the 80 mm receipt layout (H25). No new dependency.
2. When owners get receipt links (WhatsApp): one edge function posts the existing receipt HTML to **PDFShift** (the free tier is enough for a pilot) and stores the PDF in a private bucket. Send a signed link. Move to self-hosted Gotenberg only if volume or PDPL makes it worth running a server.
3. Don't draw Arabic PDFs by hand with `pdf-lib`, and skip WebUSB printing (it doesn't work on iPads).

Why it matters for Touq: at the pilot you will want facts such as "how long does a booking take?", "do receptionists use the Reminders page?" and "where do errors happen?". The HCI ideas in these reports are guesses until you measure.

Risks for Touq:
- **Screen recordings can capture owner names, phones and diagnoses** shown as text, not only in inputs. Set `maskTextSelector: '*'` (mask all text) or turn replay off.
- PDPL: analytics is a transfer abroad and another processor. List it in the DPA, and don't send names or phones as event properties: use the staff id and role only.
- Lock-in is low: events are plain `capture('booking_saved')` calls.
